# System Architecture Sketch

hloop is a single stdlib-only Go binary (no third-party dependencies, see GUARDRAILS.md). A human configures a project once; `hloop run` then drives coding-agent CLIs ("harnesses") turn by turn, checks their work itself, and records everything in a ledger. Agents talk back only through `hloop` subcommands. Keep this file in sync with DECISIONS.md.

## Layers / Components
1. **cmd/hloop**: the CLI. `main.go` maps command names to `cmd*` functions; `cmd_*.go` hold the commands (project setup, ledger, run, spec, release, notify, schedule, trust, quality gates, tour). It owns the agent allow-list (`allowedForAgents` in `cmd_trust.go`, enforced in `main.go` when `$HLOOP_AGENT` is set). It contains no loop logic: commands call into `internal/*`.
2. **docs**: `embed.go` embeds the reference pages in `docs/reference/*.md` so `hloop docs` works offline and matches the installed version. (INSTALL, ADAPTERS, MIGRATING and PUBLISHING in `docs/` are repository documents, not embedded.)
3. **internal/store**: everything persisted. `Project` (root plus `.loop/`), `Config` (config.json: limits, agents, pipeline, gates, guards, notify), the `Ledger` (tasks, criteria, blockers, decisions, ideas, lessons, reviews, releases) with `UpdateLedger` (locked read-modify-write), `State` (run state, run.lock, stall counters), the inbox (`inbox.jsonl`, held items from the phone), the project registry, global notify settings, `render.go` (generates PROGRESS.md, DECISIONS.md, LESSONS.md, PROGRESS_LOG.md from the ledger) and `trust.go` (fingerprint). Cross-process safety is `withFileLock`, an O_EXCL lock file (stale after 30s, 15s wait), plus `writeAtomic` (temp file and rename).
4. **internal/adapter**: describes how to drive a harness as data: an argv template with a `{prompt}` placeholder, run with no shell. Built-in adapters, user and project adapters (JSON), tier (model) args, a continue-session variant, `Run` (process-group kill on timeout, tail buffer, per-run log) and `Classify`, which maps exit code and output tail to `ok | rate_limited | timeout | error | missing`.
5. **internal/engine**: the loop. `engine.go` (turn loop, `runAgentWith`, `buildPrompt`, ledger commit, digest), `guard.go` (before/after file snapshots; reverts writes outside an agent's mode scope: `loop-only` = `.loop/`, `docs` = documentation paths; `write` agents are unrestricted), `detect.go` (git detectors, below), `verify.go` (gates, red/green TDD proof, `VerifyDone`), `report.go` (per-task completion report), `release.go` (version bump, preflight, release brief and output checks, release commit and annotated tag; never pushes).
6. **internal/notify**: delivery to a phone. `Dispatcher` sends events to ntfy and/or Telegram (plus desktop notification); `Bot` is the Telegram listener that accepts a fixed command set and inline buttons (approve/reject held notes, answer blockers, pause/resume). Events are filtered by `notify.events` in config.
7. **internal/scaffold**: creates and upgrades `.loop/` (config, planning documents, default prompts, initial ledger), discovers existing repos for `adopt` (stack, docs, test hints, secret-looking files), agent profiles, and `speccheck.go` (`hloop spec check`: vague wording, missing `:: how verified`, missing spec sections, unfilled template markers).
8. **internal/sched**: installs OS schedules that run `hloop run` again (cron on Linux, launchd on macOS, Task Scheduler on Windows) and the phone listener at login. Generates entries; it does not run the loop.

## How a turn flows (`Engine.loop`, `engine.go`)
1. Pre-turn: drain the inbox into steering notes; under the ledger lock, stop if any blocker is open, else `Promote()` the next pending task to current and record `StartCommit`. No task left: notify "complete".
2. Prompt: `buildPrompt` = the role prompt from `.loop/prompts/` (or the built-in default) plus a generated "Run context" block: project, agent, mode, `$HLOOP_BIN`, guardrails pointer, CURRENT TASK with details, spec path, acceptance criteria and how to mark them, the gates hloop will run, the TDD protocol if on, steering notes, active lessons.
3. Adapter run: `runAgentWith` first calls `RequireTrust`, snapshots the tree (guarded modes) or takes a git point (write mode), then `adapter.Run` with env `HLOOP_BIN/PROJECT/AGENT/ROLE/MAX_REVIEW_CYCLES`, the agent timeout and a log in `.loop/runs/`. A failed "continue" session is retried fresh.
4. Classification: `rate_limited` ends the run and sets `RetryAfter`; `missing` is a setup error; `error`/`timeout` count toward `max_consecutive_failures`.
5. Scope guard and detectors (after the run): `enforceGuard` reverts out-of-scope writes for `loop-only`/`docs` agents (an unrevertable one raises a blocker). For `write` agents `detect` compares against the pre-run git point: `history_rewrite`, `protected_commit` (commit on main/master), `dependency_change` (manifest or lock file changed), `mass_delete`. Each is configured `block` (opens a blocker), `notify` or `off`, and is logged on the task as a guard event.
6. Verification: `verifyFinished` re-checks every task that became done this turn: all Must criteria marked pass, every applicable gate (run in the worktree or on an `export` of the last commit), and, with `tdd: on` for code tasks, that the gates fail at the recorded red commit and pass at HEAD on clean copies. A failure reopens the task, bumps `GateFails`, queues the reason as a note for the next turn and notifies. A pass stores `Verified` and writes `.loop/reports/<ID>.md`.
7. Ledger commit: `commitLedger` commits only `.loop/` (if `commit_ledger` and a git repo) after the turn, after each secondary agent, and after reports. Views are regenerated by `RenderViews`.
8. Post-turn: blockers raised are announced and stop the run; `checkStall` opens a blocker after `max_stalled_turns` turns without a finish; secondary agents (reviewer, etc.) run when `due` (`every_turn`, `after_milestone`, `every_n_turns`, `on_run_end`); a reviewer's `changes_requested` becomes tasks; finally pause and loop until `max_turns_per_run`.

## Security boundaries
- **Trust fingerprint** (`store/trust.go`): a SHA-256 of `config.json`, `GUARDRAILS.md` and every file under `.loop/adapters/` and `.loop/prompts/`, recorded in `$HLOOP_HOME/trust.json` keyed by the resolved project path. These files decide which programs start and what the agents are told. `RequireTrust` is called before every harness start and gate run (engine, release, interactive agents); a mismatch (cloned repo, or an agent edited them) refuses to run until a human runs `hloop trust`. Commands that legitimately change them wrap the work in `PreserveTrust()`, which re-records only if the project was trusted before. The 0.3.0 combined-hash formula must stay unchanged (backward compatibility).
- **Agent command allow-list** (`cmd_trust.go`): when `$HLOOP_AGENT` is set, only the listed subcommands run (task add/done/ac/..., blocker add, idea/lesson/decision add, review submit, spec check, read-only views). Setup, config, trust, run, schedule, notify, blocker/decision resolve and `docs --export` are refused. This stops mistakes and simple prompt injection; it is not a sandbox, since an agent with a shell can edit files directly.
- Supporting: names and prompt paths are validated (`ValidName`, `ValidPromptPath`, `SafeName`); adapters are argv arrays with no shell; run logs are 0600; the Telegram bot only answers paired chats and scrubs the token from errors; phone-submitted notes are held until approved (`remote_tasks: approve`).

## State
- **Per project, `.loop/`**: `config.json`; `ledger.json` (source of truth); `state.json` (paused, retry time, turn totals, stall counters, last reviewed commit); `run.lock` (one run at a time); `inbox.jsonl` and `inbox.archive.jsonl`; `*.lock` helper files; `PRD.md`, `ARCHITECTURE.md`, `CURRENT.md`, `GUARDRAILS.md`, `specs/`, `prompts/`, `adapters/`; generated `PROGRESS.md`, `DECISIONS.md`, `LESSONS.md`, `PROGRESS_LOG.md`; `reports/`, `reviews/`, `release/`; `runs/` (logs, newest 100 kept).
- **Per user, `$HLOOP_HOME`** (default `<user config dir>/harness-loop`): `projects.json` (registry), `trust.json`, `notify.json` (0600, ntfy topic and Telegram token), `telegram-state.json`, `adapters/` and `profiles/` (user-level extensions).

## Tests
- **Unit** (`internal/*/_test.go`, about 60 tests): store (ledger, locking, trust, security), adapter (arg expansion, classification), engine (guards, detectors, versions), notify (formatting, bot parsing), scaffold (spec check, discovery), sched (cron/plist/schtasks text). Run with `go test ./...`; CI gates are `go vet ./...` and `go test ./...`.
- **End to end** (`cmd/hloop/*_test.go`, about 66 tests): `TestMain` builds the real binary once and writes a POSIX shell "fake harness" (`fakeScript` in `e2e_test.go`). Each test creates a temp git repo with its own `HLOOP_HOME`, points an adapter at the script and runs `hloop run`. The script behaves differently per role (builder, reviewer, adopter, planner, spec-writer, tech-writer, interviewer) and per `FAKE_MODE` (ratelimit, fail, silent, noac, gate, tdd, tddcheat, rewrite, deps, block, trespass...), and acts only through `$HLOOP_BIN`. `security_e2e_test.go` covers trust and allow-list. Skipped on Windows. No test calls a real model or network.

## Key technical risks to validate early
- The allow-list and scope guard are not a sandbox: a `write`-mode agent can edit `.loop/config.json`, hooks or CI directly. Trust catches only fingerprinted files, and only at the next start. Unattended use needs a VM or container.
- Classifying harness output (rate limit vs error) relies on text patterns that differ per CLI and version; a wrong class either burns the failure budget or sleeps for hours.
- Detectors and verification depend on git state: no repo disables the guards, and a "done" is only as strong as the configured gates (none means accepted on the agent's word). `export` gates fail on projects whose tests need installed dependencies.
- Lock files are O_EXCL with 30s staleness; a crash leaves locks that expire, and a slow writer past 30s could lose the lock. The ledger is rewritten whole each time.
- Cross-platform behaviour (process-group kill, cron/launchd/schtasks, the Telegram long-poll listener) is tested mostly on Linux; the Windows and macOS paths are lightly covered.
- `.loop/` formats must stay loadable by 0.3.0 ledgers and configs; adding fields is safe, renaming or removing is not.

## Reference test set
- `go vet ./... && go test ./...` (all of the above).
- Fake-harness scenarios that must keep passing: happy path (`ac`), rejection and retry on a failing gate (`gate`), rate-limit backoff (`ratelimit`), consecutive failures (`fail`), stall blocker (`silent`), TDD pass and cheat (`tdd`, `tddcheat`), history rewrite and dependency detectors (`rewrite`, `deps`), blocker stop (`block`), tampered config refused (`TestTamperedConfigIsRefusedUntilAHumanApproves`).
